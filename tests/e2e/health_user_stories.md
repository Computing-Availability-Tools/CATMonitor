> **配套产物**：`tests/e2e/health_testcases.xmind`（61 个测试点，按功能/边界值/异常/业务规则/非功能性五维度拆解，P0/P1/P2 标注；其"用户故事索引"分支的节点备注即本文各条描述）。
>
> **素材来源**：由 `features/health/HEALTH_SPEC.md` + `WEIGHT_SPEC.md`（v0.3.6）反向改写为用户视角，经评审定稿。与原始需求冲突时以原始需求为准。

## US-001 计算健康总分与等级

作为运维工程师，我希望 CATMonitor 基于一轮全量采集的指标计算 0-100 的服务器健康总分并映射 Excellent/Good/Warning/Critical 等级，以便一眼判断服务器整体健康状态。

**业务规则**：
1. 总分 = 7 个部件得分之和；
2. 等级边界：≥90 Excellent、75-89 Good、60-74 Warning、<60 Critical（89/90、74/75、59/60 为关键边界）；
3. 输出含 server_type（cpu_only | accelerated）与评估时间戳。

## US-002 权重方案自动检测与覆盖

作为运维工程师，我希望系统按服务器实际加速卡配置自动选择权重方案，以便纯 CPU、2 卡、4 卡、8 卡 NPU 服务器各自获得合理的评分权重而无需手工配置。

**业务规则**：
1. 有 GPU 指标 → accelerated_8card；
2. NPU 按唯一 npu_id 标签数计卡：≥5 卡 → 8card、3-4 卡 → 4card、1-2 卡 → 2card、无加速卡 → 使用传入方案（weight_scheme 配置，默认 auto 解析为 cpu_only）；
3. 卡数统计 fallback 为 npu_num/2（双芯片共享一张卡；结果为 0 时取 1，如 npu_num=1）；
4. 检测到 GPU/NPU 指标时自动检测结果优先于传入方案（Evaluate 内部覆盖，幂等）；
5. 无 BMC（无 chassis 指标）时 Chassis 权重并入 CPU、Chassis 记 0（四方案 CPU 有效满额变 35/30/25/25）；
6. 四套方案权重各异且总和为 100（cpu_only: 25/25/30/0/10/10；2card: 20/20/20/20/10/10；4card: 15/15/20/30/10/10；8card: 15/15/15/35/10/10）。

## US-003 部件扣分规则（关注点预算制）

作为运维工程师，我希望每个部件按预定义扣分规则从满额扣分并给出扣分明细，以便定位具体是哪条规则触发、扣了多少。

**业务规则**：
1. 每部件的关注点预算总和 = 满额的 100%（最差情况归零）；
2. 同关注点分级互斥、只扣最高档（如 CPU 温度 >85°C 扣 30% 与 >75°C 扣 15% 不叠加）；
3. 部件得分下限 0；
4. 每条扣分记录规则名与分值；
5. 阈值示例：CPU 使用率 >90%/80%、内存 UCE >0 扣 30%、Disk SMART 失败扣 50%、NPU 掉卡 >0 扣 20%、机箱进风 >40°C/出风 >60°C 扣 50%。

## US-004 多卡最差聚合

作为算力集群管理员，我希望 GPU/NPU 多卡场景按"最差卡"触发扣分，以便单张异常卡即可拉低部件健康分、不被好卡平均掩盖。

**业务规则**：
1. 每条规则跨卡取最差值触发；
2. 掉卡（card_drop>0）本身构成独立规则；
3. 多芯片（chip_id）归并到所属卡。

## US-005 指标缺失优雅降级

作为运维工程师，我希望某部件指标因外部工具缺失而未产出时，评估不报错、不误扣分，以便监控工具部分不可用的机器上仍能获得其余部件的有效评分。

**业务规则**：
1. 单条规则缺指标 = 不触发；
2. 整部件分组为空 = 跳过该部件不扣分；
3. 评估正常返回、Score 为已评估部件之和。
